# GBC版Wizardry I：お金倍率の解析と実装

戦闘後の宝箱報酬について、原作が人数で分配した1人分のお金を×1／×8／×16／×32／×64／×128／×256にします。経験値倍率とは独立して設定できます。

| 用途 | CPUアドレス・形式 |
|---|---|
| 戦闘から宝箱処理への呼出 | ROMバンク1 65DB〜65E0、バンク6 5D64へfar call、復帰先65E1 |
| 金額の抽選・計算 | ROMバンク6 5F2B〜5F78 |
| 人数による除算 | 5F79: CALL 28FE、5F7C: CALL 0E91 |
| 1人分の金額 | HRAM FFB8〜FFBD、6バイト・ビッグエンディアンpacked BCD |
| 倍率化のタイミング | 5F88のLD (DE),Aで最終バイトFFBDを書込、コールバックPC=5F89 |
| 現在バンクの検査 | C049=6、FF70の下位3ビット=1 |
| 呼出フレームの検査 | SP上の保存AFを飛ばし、far call復帰先000F、呼出元ROMバンク1、復帰先65E1を確認 |
| 配分対象 | D543 + パーティー位置の戦闘状態値が2未満 |
| キャラクターの所持金 | 固定WRAM C10A + 人物番号×6Eh + 11h〜16h |
| 加算 | 5FB9で共通BCD加算0DDB、5FBD〜5FC7で人物へ書戻し |
| 表示 | 5FCA以降で配分額を数値表示形式へ変換 |
| 通常セーブ | SRAMバンク0 A02B + 人物番号×6Eh、所持金は+11h〜16h |

倍率を掛ける対象は配分後の作業領域だけです。所持金全体、店の取引、銀行や金の受け渡しには掛けません。戦闘からの呼出フレームを照合するため、同じ宝箱処理でも別の呼出元には介入しません。

ROMヘッダーと配分・加算・呼出命令列で対応版を判定し、ハッシュは使用しません。ROMを書き換えず、書込フィルターでBCDの各桁を検査して倍率化します。倍率計算は64ビットで行い、原作の12桁上限999,999,999,999で飽和させます。所持金への加算も原作のBCD飽和加算をそのまま使用します。

## 検証

経験値解析時の実戦闘fixtureから宝箱報酬まで進め、倍率化前の1人分が15、6人分の所持金とSRAMの増分が15で一致することを確認しました。×8なら120、×256なら3,840です。

`gold_wizardry1_test` は経験値×1／×256と、お金の全7倍率×全5速度を組み合わせた70条件で検証します。表示の文字数による乱数の変化で、後続の宝箱処理・基礎金額が変わる場合があります。検証では金額加算直後に人物データを比較し、その後はBで後続の宝箱操作を進めます。後続の入手アイテム・罠などの差は倍率による直接の書換と区別します。

- 同じ経験値・速度設定では、お金倍率を変えても倍率化前の金額が一致。
- 6人分の所持金増分と通常セーブが一致し、金額加算直後の所持金以外の人物項目は同じ。
- 戦闘状態1には加算され、2は除外される原作条件を維持。
- 所持金上限直前への加算とSRAM保存、配分額の倍率計算の双方で12桁上限を維持。
- 別バンク・別呼出元・不正BCDの拒否、ステート復帰後の両倍率保持を検査。
- 既存の経験値テストで、両倍率×1・等速時の原作コア状態との完全一致を確認。

CMakeの `GBWIZ_WIZARDRY1_REWARD_CHECKPOINT` と `GBWIZ_WIZARDRY1_GOLD_CHECKPOINT` にローカルの配分直前ステートを指定するとCTestへ登録されます。ROM・セーブ・検証用ステートは配布物に含めません。

Androidには `CoreTest.testWizardry1GoldRewards` を追加しました。経験値解析と共通のcache fixture（`test.gbc`、`wizardry1-before-experience.bin`）で全倍率のSRAM反映とリセット後の設定保持を検査します。今回のAndroid実機実行は未実施です。全敵・全宝箱・全人数・全状態異常の網羅検証ではありません。

検証結果：既存を含むWindows CTest全35件が成功しました。Windows Release、Android Debug（arm64-v8a／x86_64）、AndroidテストAPKのビルドも成功しています。今回のAndroid実機操作は未実施です。
