# GBC版Wizardry I：キャラクター属性変更の解析

その後、GBC II／IIIにも対応しました。[II・IIIの解析と検証](wizardry23-alignment-analysis.md)を参照してください。以下の対象範囲の記述はI実装時点の記録です。

2026-11-01。ローカルROMの逆アセンブルと、既存の全呪文習得・善悪混合処理を照合した記録です。GBC版Wizardry Iの属性編集を実装しました。ROM判別にハッシュは使用しません。

## 確認できた格納形式

| 項目 | 位置・形式 |
|---|---|
| 登録人物 | C10A＋登録番号×6E、110バイト、20人 |
| 属性 | レコード＋0Aの下位2ビット。善0／中立1／悪2、3は対象外 |
| 1人目の属性 | C114 |
| 施設内の人物作業領域 | C9A2、属性はC9AC |
| 通常セーブの人物 | SRAMバンク0 A02B＋登録番号×6E、属性はA035＋登録番号×6E |
| パーティー | C103〜C108が登録番号、C109が人数 |

レコード＋0Aは属性専用の1バイトではありません。作成処理のバンク6 5286〜528Fは選択値を上位へ格納し、52F6〜5300は属性選択値をAND 03してC9ACにORします。表示処理のバンク3 52D5〜5318も同じバイトから属性と他の情報を別々に取り出します。変更式は `(元の値 & FC) | 新属性` とし、上位6ビットを必ず保持する必要があります。

原作自身の属性更新も確認しました。バンク5 7616〜762Eと7632〜7652は、参加人物を276Bで取得し、レコード＋0Aの下位2ビットを更新します。どちらもAND FCで他の情報を保持しています。処理全体のイベント上の意味は今回の解析対象外です。

## 原作の参照処理

- 固定バンク2776：C10A＋登録番号×110を取得。276Bはパーティー位置からC103の登録番号を取得して同じ処理へ合流します。
- バンク1 55D3〜5602：参加人物を毎回取得し、＋0AをAND 03して善悪マスクを集計。外伝1のようなパーティー欄上位ビットの属性キャッシュ更新は、この処理には不要です。
- バンク3 52FE〜530C：＋0Aの下位2ビットで5334の3要素テーブルを参照して表示します。
- バンク3 58B5〜：酒場の候補生成も＋0Aの下位2ビットを参照します。表示済みの候補一覧は別途再生成の確認が必要です。

## 保存と作業領域の同期方針

既存の全呪文習得の人物追跡・拒否条件を再利用しました。以下は実装方針で、検証結果は末尾に記載します。

1. 対応ROMの属性生成・表示・原作更新・人物取得・保存命令列を照合する。Wiz2／3は別途確認する。
2. 戦闘・転送中・空欄・範囲外・未確認版を拒否。WRAMとSRAMの対象人物の識別を確認する。
3. 選択人物の登録WRAMとSRAMについて、それぞれの元の値の上位6ビットを保持して属性のみ更新する。
4. 施設のC9A2作業領域が選択人物に対応するときはC9ACも同様に更新する。同名人物やステート復帰後の対応が不明な場合は推測しない。未保存のHP等は保持する。
5. SRAM A000〜ABFDの8ビット加算値をABFE、反転値をABFFへ更新する。固定バンク2B30が原作の加算処理。
6. 既存の通常セーブ経路で保存する。2C03はC0F0→A011へ08B2バイト転送し、2C3Cからの読込は逆方向に復元する。

人物作業領域を更新しないと、施設内操作の続行によって編集前の属性に戻る可能性があります。呪文編集と同様、登録人物だけへの書込みでは足りません。

## 確認項目と残る検証

- 全3属性・登録人物ごとに、上位6ビット、他項目、他人物、パーティー番号・人数の保持。
- 施設内の作業人物と編集人物が同じ／異なる場合、同名人物、転送中断時の拒否。
- 原作の人物保存後・通常セーブ再読込後・ステート復元後の属性。
- 原作表示と善悪集計の実行結果、酒場候補一覧の再生成、善悪混合ON／OFFとの併用。
- Windows／Androidの1行の左右操作と保存失敗時の表示。

属性が条件となる職業等の原作制限を解除する機能は含めません。

解析段階では、外伝1の属性編集、GBC I〜IIIと外伝I〜IIIの既存呪文編集、デスクトップの計25テストで既存処理を確認しました。今回のGBC I属性編集の検証は以下に記録します。

## 実装と検証（2026-11-01）

Windows／Androidとも、キャラクター選択後の「属性 ‹ 善／中立／悪 ›」を左右で変更し、通常セーブへ保存します。Aでは属性を変更しません。Androidは行の左右タップにも対応します。GBC II／IIIは今回の対象に含めず、「対象外」を維持します。

全呪文習得の人物編集経路を共通化し、登録WRAM・通常セーブ・対応する施設内作業データの各々の上位6ビットを保持して、下位2ビットだけを変更します。通常セーブの検証値も更新します。原作の属性イベントや職業条件は維持します。

`alignment_wizardry1_test` は迷宮・町・酒場・酒場人物一覧・宿屋人物一覧・宿屋部屋選択の6状態を使用し、登録6人×全3属性×上位ビット3パターンを検証します。対象以外の人物・パーティー・HP等の保持、施設内の作業データ同期と別人物の作業データ保持、再適用の同一性、ステート復元、原作のセーブ読込処理による復元を確認します。戦闘・割込で中断された転送・空欄・別人物・同名で対応不明な作業データ・範囲外・未確認命令列は拒否します。

全イベント・全施設でのプレイ操作、表示済み酒場候補の自動再生成、保存失敗時の実機操作、タッチ操作の縦横確認は今回の網羅検証には含めません。酒場の候補一覧はBで戻り、入り直して再生成してください。

Android実機では検証専用ID `jp.gbwiz.alignmentcheck` を更新し、GBC Iの対象選択・Aでの非変更・左右の循環・上位ビットと他のセーブ領域保持を含むCharacterFlowTest全5件が成功しました。既存の正式署名アプリ・その保存データは維持しています。

最終確認：Windows Releaseビルド、CTest全79件が成功しました。Android Debug（arm64-v8a／x86_64）とテストAPKのビルドも成功しました。
