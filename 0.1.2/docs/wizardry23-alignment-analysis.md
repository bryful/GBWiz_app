# GBC版Wizardry II・III：キャラクター属性変更

2026-11-01。Wiz Iと同じキャラクターサポートの「属性 ‹ 善／中立／悪 ›」を左右で変更します。Androidは行の左右タップにも対応します。Aでは属性を変更しません。通常セーブにも反映します。

## 作品別の照合

ローカルROMを逆アセンブルし、各作品の作成・属性表示・原作属性更新・善悪集計・人物取得・保存処理を確認しました。ROMヘッダーと命令列で識別し、ハッシュは使いません。未確認の命令列では属性編集を有効にしません。

| 処理 | Wiz II | Wiz III |
|---|---|---|
| 作成時の属性格納（バンク6） | 5348〜5354 | 52ED〜52F9 |
| 属性表示（バンク3） | 52FE〜530C | 52FE〜530C |
| 原作の属性更新（バンク5） | 76A9〜76C1、76C5〜76E5 | 761C〜7634、7638〜7658 |
| 善悪集計（バンク1） | 5A1E〜5A4D | 58AA〜58D9 |
| 参加人物／登録人物取得 | 2763／276E | 2731／273C |
| 通常セーブ書込／読込 | 2BFE／2C37 | 2BC9／2C02 |
| セーブ検証値の加算 | 2B2B | 2AF6 |

両作品とも登録人物はC10A＋登録番号×6Eの110バイト、属性は＋0Aの下位2ビット（善0、中立1、悪2）です。人物作業領域はC9A2、属性はC9AC。通常セーブはSRAMバンク0のA02B＋登録番号×6Eに人物を保持します。

原作の属性更新にも `AND FC` があり、上位6ビットを保持します。製品側も `(元の値 & FC) | 新属性` とし、登録WRAM・SRAM・対象人物に対応する作業データをそれぞれの元の値から更新します。未保存のHPなどは変更しません。

セーブ検証値はA000〜ABFDの8ビット加算値とその反転をABFE／ABFFに保存します。人物の追跡、同名で対象が不明な場合の拒否、戦闘・転送中の拒否は既存の全呪文習得と共通です。パーティーは登録番号を保持し、善悪集計時に人物の属性を読みます。属性の複製キャッシュは追加しません。

## 検証範囲

既存の属性テストを作品別の原作読込処理・未確認命令列チェックへ対応させました。迷宮・町・酒場・酒場人物一覧・宿屋人物一覧・宿屋部屋選択の各状態で、全登録人物×3属性×上位ビット3パターンを検証します。

上位ビット・他項目・他人物・パーティーの保持、施設内作業データの同期、未保存HP保持、別人物の作業データ保持、再適用の同一性、ステート復元、原作セーブ読込での属性復元を確認します。空欄・範囲外・戦闘・割込で中断された転送・保存側の別人物・同名で対応不明な作業データ・未確認命令列の拒否も対象です。

Androidの操作テストも3作品で共通化し、対象選択だけでは変更しないこと、Aでは変更しないこと、左右の循環と表示値、上位ビット・他のセーブ領域の保持を検証します。

表示済みの酒場候補は原作の再生成を待つため、Bで戻って入り直してください。職業等の原作条件は解除しません。全イベントを通した長時間プレイと、今回の変更に対するタッチ操作の縦横確認は網羅検証に含めません。

## 検証結果

Windows Releaseビルド成功。属性変更18件（3作品×6場面）、外伝1の属性、呪文編集、善悪混合等を含む関連CTest全49件が成功しました。Wiz IIの検証データには7人目以降も登録されているため、空欄を登録番号から推測せず、全登録人物を列挙してテストしています。

Android Debugのarm64-v8a／x86_64とテストAPKのビルド成功。接続端末ではCharacterFlowTest全7件（GBC I／II／IIIの左右属性変更と外伝1の既存操作）が成功しました。既存の正式署名アプリと保存データを維持し、検証専用ID `jp.gbwiz.alignmentcheck` のみ更新しました。
